# Zig 服务协议适配准备与小容量验证

状态：0.3.5 本地候选，未提交、部署或修改真机服务。systemd 新装已接入自动选择 Zig。

## 服务协议

Go 服务的 JSON 配置为 `token`、`routeridx`、`supplierCode`；Zig 使用 YAML 的
`userToken`、`routerIdx`、`supplierCode`。不能仅替换二进制并复用旧 `run` 包装器。

新增 `sources/ddnsto/linux-zig-config.sh`：

- 只生成配置和启动包装器，不写系统文件、不启动服务。
- 使用现有 jq 处理单个 JSON 对象，保留上述字段，支持数字和数字字符串设备编号。
- 检查类型、编号范围、文件大小、路径；拒绝不认识的设置，避免静默丢失配置。
- YAML 使用 JSON 引号编码；启动包装器复用既有 POSIX 引号编码，不拼接执行配置内容。
- 配置指定独立状态目录、日志目录、回环 HTTP 地址，并关闭 WebDAV。
- Token 只在配置中，不放进启动命令参数或包装器。

后续接入进度：配置模块与 `linux-zig-service.sh` 已加入本地 0.3.5 候选，
服务协调器在 start/restart 前提供应用钩子；只有精确匹配已生成 Zig 包装器的安装
才生成运行 YAML，标准客户端保持原行为。新装产品选择、sudo 准备、root 再校验、
配置和服务维护已接入；新装标准包放不下时使用固定摘要的裸 Zig，已有版本不自动换实现。
发布前仍需区分以下验证边界：

1. 产品选择与真实 sudo 用户切换已覆盖；空间不足与禁止降级有独立测试。
2. 生命周期隔离测试使用客户端/systemctl 替身，不等同真实 systemd 自启动验收。
3. 缓存、更新比较、跨版本凭据识别；当前只识别已审核的 Zig 版本与摘要，未来升级需保留历史识别能力。
4. 确认旧 boot 配置的格式和设备身份能否跨 Go/Zig 保留，不能只凭字段同名承诺。
5. ARM 实机与真实 systemd 服务验收仍待执行；当前不承诺云端在线或跨实现身份继承。

## 启动与恢复接入

- JSON 是唯一权威配置；YAML 为派生数据，在协调器启动前按当前 JSON 重新生成。
- 生成使用私有临时文件和 native 有界原子写入，不直接截断旧运行配置。
- 回滚先恢复 JSON、unit 和 current，再启动；钩子读取恢复后的 current，不使用可能过期的 SERVICE_EXEC。
- 错误配置、运行配置软链接被拒绝，旧文件不被覆盖，服务不启动。
- 管理凭据接受审核 Zig 的精确包装器、版本和摘要，不将任意类似包装器视为可接管安装。
- 此钩子不取代完整的 systemd 生命周期验收，也不改变现有标准安装器的产品选择。

## 真实小容量文件系统

扩展 `tests/ddnsto_process_zig_native_test.py`：维护者在独立 mount/network namespace
创建 **3 MiB tmpfs**，以非 root 用户、临时 HOME 运行实际 Zig 和 zsetup。
storage 查询使用真实文件系统结果，不模拟 available_bytes。安装后再占用 1500 KiB，
确认剩余不足 1 MiB，再验证重复执行复用、停止与启动。

下载边界仍用已审核 SHA-256 的本地二进制替代网络；zsetup 本体位于测试小文件系统之外。
因此该用例证明的是业务进程安装阶段，而非整台设备只有 3 MiB 也能从公网完成自举。
测试退出清理进程和挂载，不访问业务网络，不操作宿主机 systemd。
